# 架构不再由人挑：目录恒要全部平台，判决画在卡片上

Status: accepted
Date: 2026-10-26
Related: `2026-10-26-platform-availability.md`（本记录取代其「默认 strict / 开关 / 平台下拉」的
UI 与默认口径，保留数据契约与 `compatibility` 求值）、`2026-10-26-install-gate.md`、
`2026-10-26-catalog-card-dialog.md`

## 背景

商城管理页曾同时提供三种架构相关控件：

- 目录工具条的「只看支持当前架构」开关（默认开，关掉才发 `platform=all`）；
- 安装条的平台下拉（只列宿主平台与 `any/any`）；
- 卡片上的「不支持当前架构」徽标（只在 `supported === false` 时出现）。

运营侧的反馈是：前两者让人以为要自己挑架构，而「找不到就提示不支持」的负面结论在默认口径下
根本看不到 —— `platform=strict` 会把整条产品从目录里藏掉。安装目标是**服务器**，不是管理员的
浏览器；页面本来就有 `target`（插件后端回报的 `runtime.GOOS/GOARCH`），没有任何理由再问人。

## 决定

1. **目录恒发 `platform=all`**：产品不再因为异架构从列表消失。服务端 `compatibility` 仍按
   `os`/`arch` 求值，`all` 只放宽可见性（沿用 `2026-10-26-platform-availability.md` §3/§4）。
2. **删除架构选择**：目录开关与安装条平台下拉都不再存在；平台由 `defaultPlatform` 自动决定
   （精确匹配 → `any/any` → 第一项）。
3. **卡片只留一枚架构判决**：`支持当前架构`（ok）/ `不支持当前架构`（warn）/
   `最新版不支持当前架构`（warn）；没有 `target` 或没有平台信息时不画（未知不是不支持）。
4. **正向判决顶掉原始平台 chip**（清单进 `title`）；负向判决保留 chip 作为解释
   （「这包其实是给 darwin 的」）。`supported === false && supportedAnywhere === false` 时
   不再叠一枚兼容徽标 —— 同一原因（架构）不说两遍。
5. **安装条说结论**：空闲且可安装、且该版本支持宿主时显示 `支持当前架构（linux/amd64）`；
   不支持的文案沿用 `installBlockedPlatform`。
6. **服务端、OpenAPI、Go 后端零改动**：`platform=strict|all` 契约保留给其他客户端，
   插件只是把它当默认值用满。

## 放弃的方案

- **保留开关但默认关**：操作者仍要理解「架构」这个概念，且默认关会让目录被异架构产品淹没。
- **把 `all` 做成服务端默认**：公开站与其他客户端会跟着变，超出本仓控制面。
- **按浏览器 UA 推断架构**：安装目标是服务器，浏览器架构是错的基准。

## 代价与重开条件

- 目录变长，跨架构产品与可安装产品混排；需要时再加「支持优先」排序，或改服务端默认口径，
  届时重开本记录。
- 旧插件后端（不回 `target`）不再有人工平台选择：`defaultPlatform` 退到 `any/any` → 第一项，
  由 core 的启动诊断做最终裁判。
- 回滚：一次 `git revert`；无 schema、契约、DB 变更。
